记忆检索：先建评测，再动手重写

旧方案是向量库加手调的重排分数，用着总觉得「她明明聊过却想不起来」。我从真实使用里挑了 81 道回忆题，其中 36 道是我真问过的，然后一步步拆开测。

结果最大的损失出在手调分数上：正确答案已经排进向量检索的前三，还会被关键词加分挤下去。换成向量与 BM25 的 RRF 融合，再横评 6 个 Embedding 模型，选了 voyage-4-large。重排模型要多花 300 多毫秒，只多答对 0 到 1 题，没有上。

代码执行：自己用和给别人用，分两套

我自己用的 CodeAct 在本机执行，会改数据的操作先弹给我确认。开放给朋友以后，访客的代码一律进 Monty（一个用 Rust 写的 Python 解释器）的沙箱：碰不到文件和网络，内存、计算时长、每段代码能调几次工具，都有上限。

我先自己写过一版解释器，后来被别名修改这类写法绕过去了，就换成了现在这套。

多用户：靠进程隔离，不靠每处传用户 id

朋友通过 Cloudflare Access 登录，后端验签确认是谁。每个访客单独起一个后端进程，数据目录物理分开，30 分钟没动静就自动退出。

代码里单例很多，要是靠每个地方都记得传用户 id，漏一处就会串数据。进程边界不会漏。

换窗口也不断片

上下文快满的时候，一个评分 Agent 判断什么时机切新会话合适。切的时候，上一段的最后几轮会带进新会话，她不会突然像换了个人；新会话聊够了，就不再带。

带过去的内容放在消息里，不占提示词的缓存断点。

成本：让缓存真的命中

提示词按变化频率分段缓存。时间、日程这类每轮都会变的内容，在这一轮第一次发送时冻结成快照，重试和工具循环都复用同一个前缀。每轮的费用和缓存命中单独记账，还能和上游的账单对得上。

76%–92%近两个月 Claude 系模型聊天请求的缓存命中率

人设对齐：按「宪法」造数据，再微调

我先把她的性格和原则写成一份「宪法」，再按条目合成 18 批、共 774 条正反例，自洽检查不过的就重新生成，然后在 Qwen3-4B-Instruct 上做了 LoRA 微调。对话流程里还接了语料自动导出，会做时间泛化和噪音过滤，保留思考过程。
